# How to run this framework from GitHub Actions

Step-by-step reference for the generated workflow at
[`.github/workflows/qaff-ci.yml`](../.github/workflows/qaff-ci.yml)
(Phase 1.9).

## 1. Prerequisites

- A GitHub repository with this generated framework checked in.
- GitHub Actions enabled for the repository (default for public repos
  and most organisation policies).
- The default `ubuntu-latest` runner image. The workflow uses
  `actions/setup-java@v6` (Temurin JDK 21) and Maven dependency
  caching (`cache: maven`); no other action is required.
- A Chromium binary on the runner if you intend to actually execute
  the `web-desktop` layer in CI. The workflow defaults
  `BROWSER_BINARY` to `/usr/bin/chromium-browser` (present on
  `ubuntu-latest`). Adjust if your runner has Chromium elsewhere.
- Repository secrets `ZEPHYR_BASE_URL` and `ZEPHYR_TOKEN` are required for the opt-in Zephyr Scale Cloud sync step.
- Repository variable `ZEPHYR_PROJECT_KEY` is optional when `integrations.zephyr.projectKey` was generated; `ZEPHYR_CYCLE_KEY` is optional.
- Repository secret(s) SLACK_WEBHOOK_URL are required for the opt-in run notification step (`ci.githubActions.notify`).

## 2. When does the workflow run?

| Trigger | What runs |
| --- | --- |
| `pull_request` | Full Maven reactor (`mvn -B verify`). |
| `workflow_dispatch` | Reactor-or-module build, controlled by the inputs below. |

`pull_request` deliberately ignores branch filters so the workflow
fires on every pull-request event. Add a `branches:` filter under
`on.pull_request` if you want to scope it further.

## 3. How to run manually

In GitHub UI: **Actions → qaff-ci → Run workflow**.

In the GitHub CLI:

```bash
gh workflow run qaff-ci.yml \
  -f application=demo-saas \
  -f layer=web-desktop \
  -f environment=local \
  -f browser=chromium \
  -f headless=true
```

## 4. How to select an application and layer

The workflow exposes six `workflow_dispatch` inputs:

| Input | Choices generated by qaff |
| --- | --- |
| `application` | `all`, `demo-shop` |
| `layer` | `all`, `web-desktop`, `api` |
| `environment` | `local`, `dev`, `staging` (logical label only — no real env is wired) |
| `suite` | Free-text JUnit 5 tag passed as `-Dgroups`. Leave empty to run every test. |
| `browser` | `chromium`, `chrome`, `firefox` (only `chromium` is wired today; web-desktop only). |
| `headless` | `true` / `false` (web-desktop only). |

Selection rules:

- If **both** `application` and `layer` are concrete values (not
  `all`), the workflow runs:
  `mvn -B -ntp -pl apps/<application>/<layer> -am verify`. Only the
  selected module and its upstream `framework-*` dependencies build.
- Otherwise the workflow runs the full reactor:
  `mvn -B -ntp verify`.

This mirrors the Jenkins runner's per-build narrowing behaviour but
keeps full-reactor as the safe default for `pull_request`.

Not every application necessarily has every layer listed in the input
choices. When both `application` and `layer` are concrete values,
the generated workflow validates the pair against the generated
application-to-layer map and fails early if the combination is not
present in the repository.

## 5. Where artifacts are uploaded

The workflow uploads three artifacts via `actions/upload-artifact@v7`,
all marked `if-no-files-found: ignore` so missing outputs do not fail
the run:

| Artifact name | Path | Notes |
| --- | --- | --- |
| `surefire-reports` | `**/target/surefire-reports/*.xml` | JUnit 5 XML — feed to any downstream report consumer. |
| `allure-results` | `**/target/allure-results/**` | Allure raw results. The workflow does **not** render an Allure HTML report; do it in a follow-up step or job if you want one. |
| `framework-performance-reports` | `framework-performance/reports/**` | Quality Impact Pack outputs (placeholder until real runners land). |

Artifacts appear under the **Summary** tab of each workflow run.

## 6. Current limitations (Phase 1.9)

- **Zephyr Scale Cloud sync is enabled.** The workflow calls
  `qaff sync-zephyr-results` after test execution. Live mode requires
  user-managed GitHub secrets; generated files never store tokens.
- Jira, Xray, TestRail, Zephyr Squad and Zephyr Data Center connectors
  remain out of scope for this generated project.
- **No provider execution is generated in CI.** The workflow can only import
  optional pre-produced k6/JMeter files via generated helper scripts.
  It does not run k6, JMeter, Gatling Enterprise, or JMH workloads. Enable
  `ci.githubActions.performanceRun` to add the offline Gatling producer step.
- **No deployment.** The workflow runs tests; it does not push
  artefacts or deploy applications.
- **No secrets** are read or required. If you later need to talk to a
  real environment, add the appropriate `secrets.*` references in a
  follow-up patch — do not hard-code anything.
- **No matrix fan-out** today. Use the `workflow_dispatch` inputs to
  pick one application/layer pair per run, or trigger the workflow
  multiple times. A matrix variant is on the roadmap.
- **`browser` choices include `chrome` and `firefox`** for forward
  compatibility, but only `chromium` is wired in the generated
  Selenium driver factory today.

## Notifications (opt-in)

`ci.githubActions.notify` is on: the pipeline ends with one step that runs
`qaff notify-run --mode live` for Slack and posts one message. Define
`SLACK_WEBHOOK_URL` as a CI secret — the URL is never stored in
config, the lock or this repository. See [`notifications.md`](notifications.md).
